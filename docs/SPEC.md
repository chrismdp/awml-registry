# AWML Registry: v1 spec

The AWML Registry stores, versions and draws AWML workflow files. Public workflows are free, and a private store for an organisation is paid on the hosted service. The code in this repo is source-available under FSL-1.1-MIT: a company may run it internally, but nobody may offer it as a competing service.

This file records what the registry does and the decisions behind it. AWML itself (spec, CLI, Go package) is MIT at github.com/chrismdp/awml; read its `SPEC.md` for what a workflow file is.

Each running server or Worker remembers the engine's answers for the files it was given, up to 200 of each kind of answer, so the same files are worked out once; an answer is found again only from the same files, and a refs check's files include the latest versions of the workflows its refs name, so a viewer only ever gets back what the files they may see give. What a page reads that doesn't depend on another read is read at once. Decided 2026-10-27 (issue #54). |

## What v1 does

- **Push and pull.** Push a workflow's one AWML 0.8 file from the CLI, the API or the MCP tools (see "AWML 0.8 files"). Every version can be downloaded as YAML or pulled with the CLI.
- **A page per version.** Each view drawn behind its own tab, at its own address, and the summary worked out from the file at push. The drawing (see "Drawings") sits in a frame the width of the column and `min(72vh, 760px)` tall, `min(78vh, 640px)` on a phone. The gallery's thumbnails are the same drawing as an SVG alone, with no frame or controls. A YAML tab shows the file itself and nothing else, with a Copy button and a Download link; a file stored in an older AWML is shown as it was pushed, under a line saying which AWML it is and that the registry draws, checks and fits it converted to AWML 0.8, and what converting it noted. A Checks tab says what checking the file found (see "Checks").
- **A public gallery.** Anyone can browse public workflows and search them by title. Anyone signed in can publish one, free.
- **Private workflows for an organisation.** Only its members can see them. In this repo's default edition every organisation may keep private workflows; the hosted edition limits that to paying organisations.
- **Private workflows on a person's own account.** Only that person can see them, up to the number the edition allows (see "Access"). Added on 2026-10-22.
- **An inventory for each organisation.** Every workflow in one table with its summary counts, plus totals across them all.
- **An audit log for each organisation.** Who pushed, who viewed a private workflow, platform or system, who joined or left, and which member changed their username. Owners can read it; nobody can change it.
- **Platforms, and where a workflow can run.** Added after v1 (see "Platforms and the fit").
- **Forks of public workflows.** Added after v1, on 2026-10-25 (see "Forks").
- **References between workflows.** Added after v1, on 2026-10-27 (see "References between workflows").
- **Systems: several workflows seen together.** Added after v1, on 2026-10-27 (see "Systems").
- **Drawings embedded on other sites.** Added after v1, on 2026-10-27 (see "Embedding").

## Drawings

Decided 2026-10-27 (issue #62), after an experiment behind `?draw=flow`: the registry draws a workflow, its implementations and a system's map its own way, in the site's look, and no longer with Mermaid. The code is in `src/server/drawing.ts` (the layout), `src/components/flow/` and `src/components/Drawing.tsx` (the page).

**The graph.** The engine gives the registry the drawing's model as JSON, with nothing laid out: `graph` for a workflow's security view or one implementation's platform view, and the same call given several workflows for a system's map (`graphJSON` in the WebAssembly; AWML 0.7.1, chrismdp/awml#129). Decided 2026-10-27 (issue #69), when it replaced reading the engine's Mermaid text back. The registry turns it into its own graph (`src/components/flow/graph.ts`): parts with their kinds, a step's kind of work, an outside action's tier apart from its label, and whether a part is marked untrusted, said in its caption, and from AWML 0.8 whether its text reaches an outside action that nothing stops, `unstopped`; scopes with their nesting, the colours the engine gives each place of a platform view, and on a map each workflow's box with its `owner/slug`, from the path the registry gave its file at; lines, each solid, dotted where it reads or writes a context, connector or surface, or thick where it publishes, with what it widens after its label, with an arrow at each end it points to, and from AWML 0.8 how it carries untrusted text, as `graph` gives it in `untrusted`: `carries`, `stopped` or `unstopped`, and nothing else; and comments as notes on the parts they are tied to. A tie and a hidden line aren't drawn, and a line one of whose ends isn't drawn is left out. A refused read ends in a cross. A line that breaks a rule is drawn red, with the words for each rule it breaks: from AWML 0.8, the line into an outside action that untrusted text reaches with nothing to stop it (see "Untrusted text"). **Every text field `graph` gives is exactly as the file wrote it, unescaped, line breaks included.** The registry folds each run of whitespace in a label into one space, as the engine's own drawing does, and puts text on the page only as React text or an attribute React escapes: never as HTML, and never in SVG built from strings (`test/drawing-frame.test.tsx` draws `test/fixtures/hostile.yaml`, whose labels are markup, a `javascript:` address and line breaks, on the server's SVG, in React Flow and on a page). Only a hex colour is taken from a place, and a violet one, such as the lavender among the engine's colours for places, is drawn as the grey of its lightness (#83). The engine is pinned in `vendor/awml`, and the tests compare its graph with what the native `awml graph` prints (`test/site.test.tsx`), and read the registry's graph against the YAML each is of (`test/flow-graph.test.ts`).

**The layout.** The server lays the graph out with ELK's layered algorithm, top to bottom, each scope a box round what it holds, with the lines that cross scopes laid out together; solid lines decide the layers before dotted ones, and lines are routed square with rounded corners. Each scope is the smallest box round what it holds, its padding and its heading, and at least as wide as its heading (#67). ELK reads how much room to leave between what it lays out from the node that holds it, so each scope is given the drawing's spacing as well: 40 pixels between parts side by side and 64 between layers, and room for each line's label, which ELK places as the line's own (#78). Without it, what a scope held was laid out at ELK's own, closer spacing. Laying scopes out nested together, top to bottom, ELK reads a scope's least size as (height, width), so the server gives it that way round: given (width, height), it made each scope as tall as its heading was wide, however little it held, and no wider, so a scope in Flow only kept its height and a heading ran over its border. Every box is sized round its text, which is broken into lines by Inter's widths, so a browser never breaks a label differently. Both layouts a page may need are made at once: the whole drawing, and Flow only. Each running server or Worker keeps the 200 layouts used last, by the SHA-256 of the graph's JSON, the switch and the engine's version, as it keeps the engine's answers. A layout holds only what the engine's graph says, never anything about who is looking, so one serves everyone who may see the drawing; the links of #55 and the boxes' pages of #61 are added for each viewer from what they may see. The page is sent the positions only: no part of ELK is ever sent to a browser (`test/drawing-server.test.ts` walks every module the browser may load). The gallery's cards lay out the whole drawing alone.

**What isn't laid out.** ELK holds the server while it works, and takes longer the more it lays out, most of all for lines that cross many layers and for scopes nested deep. So the server lays out a drawing of at most 80 parts, scopes and notes, 120 lines, 20,000 characters of labels and scopes nested 8 deep (`LIMITS` in `src/server/drawing.ts`), and a bigger one not at all: its page says "This workflow is too big to draw here.", or "This map is too big to draw here.", and its gallery card shows no drawing. A note isn't laid out, but it counts as a part, and each part or scope it is on as a line. Measured in workerd on 2026-10-27, one layout of 120 lines, each as long as it can be, took 350 ms with no nesting and up to 410 ms with scopes nested 8 deep; the review measured 560 ms at 8 deep, 1.3 s at 16 and 6.5 s at 50. A page lays out the whole drawing and Flow only one after the other, and they are the same size when Flow only leaves nothing out, so at the limits a page's first view takes about a second at worst, and its layouts are kept after that. The largest workflow on awml.io holds 53 parts and 73 lines, nested 2 deep. A drawing whose layout fails says "This workflow can't be drawn here.", or the same of a map, never ELK's error, and the server logs why. Both answers are kept as a layout is, so neither is tried again on the next request, and the limits bound how much the 200 kept layouts hold. Reading the engine's graph looks at each part, line and comment once, and breaking a label into lines looks at every character once, so neither takes longer than the graph is big.

**On the page.** The server's SVG of the drawing comes with the page, fitted to its frame, so a browser that runs no scripts sees it whole: its links work, and a note shows on hover. In a browser that runs them, React Flow takes over from just where the SVG shows the drawing, drawn by the same markup, and the SVG is hidden only once React Flow shows, so nothing moves or flickers; it is then only tidied where it overlaps. A part can be dragged, and its lines follow it, square as the server's are (#67): a line whose end has moved leaves the side of one end that faces the other, turns halfway between them and goes into the other, its corners rounded and its label on it, as near halfway as it can be without covering a part; a line whose ends haven't moved keeps the server's route. Two boxes with less than 24 pixels above and below each other, but that much beside, are joined side to side, so a line never runs along a box's edge (#78). Each label is drawn above every line, as the SVG draws it. While the pointer is over a part, or the keyboard is on one, everything not connected to it is knocked back in its own colours, leaving only the part, the lines with it at either end and their labels, the parts at their other ends and the notes tied to it, and so it stays while the part is dragged; a scope is never knocked back. A touch, or a pen, has no hover, so a tap on a part lights it just so, and a second tap on it follows it as a click does, if it leads anywhere; a tap on another part lights that one instead, and a tap on the background, a line or a scope puts the light out. A workflow's box on a map drawn round what it holds is a scope, so it lights nothing, but it too opens its page on the second tap, not the first. A finger that moves more than 3 pixels, the distance that starts a part's drag, or a second finger, as in a pinch, makes no tap, and a tap on a note's icon opens the note, as before. A mouse's click follows a part at once, as it always has (decided 2026-10-28). A scope's background pans. The frame takes the focus: the arrow keys move the drawing, `+`/`=` and `-` zoom by 1.25, `0` shows it at 100% and `f` fits it; a mouse drags the background and zooms with Ctrl or ⌘ and the wheel, or a double-click, while a plain wheel still scrolls the page; one finger drags, two pinch. It opens fitted, the whole drawing centred in the room the switches and zoom buttons leave, never above 110%, and is fitted again on a resize until the reader moves it. In the frame's top-right corner: Flow only; in its bottom-right: +, − and Fit. A browser without scripts doesn't show them. Nothing a reader does to the drawing is kept.

**Kinds of part.** Each kind has its own shape, its corners the same however tall the part is: a trigger a pill, a step a rounded card in its decider's colour, data a cylinder, a connection a hexagon, an outside action a tag pointing out with its tier, a surface a window. Each says its kind, and a step its verb, small above its label. A scope is a soft card with its name at the top and who it is for on lines of their own under it, smaller and in the site's muted ink, broken to fit the least room what the scope holds leaves, but never narrower than 200 pixels: a narrower scope is made wider, and its heading as tall as its lines (#67). A scope inside another alternates white and grey.

**Moving the drawing (#67, #78).** Once the page runs, the drawing starts just where the server's ELK layout put it, which is spaced for it, and is what a browser without scripts sees. There are no forces: nothing pulls or pushes a part but what overlaps it. The opening only tidies what overlaps: a part that overlaps another, 8 pixels clear, is nudged out of its way, the two sharing the move, and a label that overlaps something slides along its line; no part moves more than 40 pixels from where ELK put it, and if that leaves as much overlapping as before, ELK's places are kept. The drawing eases there over 0.9 seconds, each part and scope from where the SVG showed it, and the view with it to fit where it rests, so it opens without a jump. On the drawings on awml.io, nothing overlaps as ELK lays them out, so nothing moves. A dragged part follows the pointer, and nothing else moves unless something overlaps it. A part it overlaps, with 8 pixels to spare, is nudged out of its way by as little as will clear it, across or down, whichever way is away from it: the shorter, or the other if that leaves it clear of every other part and is at most twice as far. A part that a nudged part then overlaps makes way for it in turn, three parts deep at most, and nothing more than 140 pixels from the dragged part ever moves. Each move of the pointer starts again from where everything was as the drag began, so a part only passed by goes back, and where the part is dropped alone decides what made way for it. A line's label takes space (#78): it stays on its line, and one that is overlapped slides along it to the nearest place clear of every part and label, 6 pixels to spare. A label on a line of a part that moved needs room between its ends, and the end deeper in the chain moves to make it; a label with nowhere clear on its line moves a nearby part off it, or, when the dragged part covers it and both its line's ends are near, its line moves out of the way, ends and all. A scope is only ever drawn round its parts and the scopes in it, with its padding and heading, as the server draws it: it grows and shrinks with them, so a nested scope is inside the one it is in, but it never moves a part, and it may overlap another scope. Nothing moves once a part is dropped, until the next drag. Lines are square between where their ends are; a line whose ends haven't moved keeps the server's route. Fit fits wherever the parts are.

**Flow only (#51).** A switch that leaves out the contexts and every dotted line, and any part no line is left to except a step or a trigger, so only the workflow's own flow shows, on a workflow's drawing and a system's map alike. It shows its own layout, made on the server with the whole drawing's, not the whole drawing with gaps: each scope shrinks to what is left in it (#67), and the drawing starts from that layout.

**Notes (#60).** A drawing never draws a note. Each part with notes, or scope, has one small note icon at its bottom right; a note tied to two parts is on both. Notes tied to nothing belong to the whole drawing, and share one icon in a strip above its top-left corner. Hovering shows the notes; a click, a tap or Enter on the icon, a button with the label "Note on" and the part's label, opens them in a small modal, which Escape, Close or a press outside closes. A note's text is only ever shown as text, never as HTML.

**Gaps (#69).** A comment whose label starts "Missing from the design" marks a gap, which `graph` gives as `gap: true`. A gap is a finding, so the part it is tied to shows it at a glance: its icon is an amber warning mark in place of the note icon, with the same tooltip and the same modal, and its button is labelled "Gap in the design on" and the part's label. A gap tied to nothing goes on the whole drawing's icon, marked as a gap, even when it is drawn in a scope.

**Untrusted text (#83).** Decided 2026-10-28 by the maintainer, for AWML 0.8 (chrismdp/awml#151), which draws untrusted text in its main view and has no untrusted view, nor the WebAssembly's `drawUntrusted` and `graphUntrusted`. The registry draws it the same way, from what `graph` gives each part and line, in the server's SVG, in React Flow, in an embed and on a gallery card alike, since all four draw the same pieces (`src/components/flow/Graphic.tsx`). A part marked untrusted, a trigger, connector or context, keeps its fill and its caption's "untrusted", and takes a thick orange outline, or a thick red one when its text reaches an outside action that nothing stops and nobody accepted the risk of; every other part keeps its own border. A line carrying the text is thick orange, up to and into whatever stops it: a review, a person's own step or a code step marked `cleans`. The line out of what stopped it is thick green, and the lines after it are drawn as they were. A standing approval that accepts the risk stops nothing, so its line stays orange. The whole way from the part to an outside action that nothing stops is thick red, its last line saying the rule it breaks, and red wins on the way to where the text branches. Each colour is a token of the drawing's (`src/components/flow/flow.css`): orange `#d67200`, green `#109a74` and red `#d0342c`, each 3:1 or more on white and on the site's ink, and each line 3 pixels wide with an arrowhead of its colour; a dotted line keeps its dashes. There is no violet or purple anywhere in a drawing: an AI step is cyan, `#c9ebf5` with `#0b6e8a`, in place of the lavender and indigo it was, which are the site's own colours for AI everywhere; a focused or linked-to part is outlined in the site's ink, not its indigo link colour; and a place's violet is drawn grey. Nor are there ⚠️ or 🛡️ marks. A workflow's page has no Untrusted tab: the registry never had one, and AWML no longer has the view (`test/drawing-frame.test.tsx`, `test/flow-graph.test.ts`).

**A file whose only mistakes are drawn red.** From AWML 0.8 untrusted text that reaches an outside action with nothing to stop it or accept the risk is a mistake, and the engine draws it as red lines, as `awml draw` does. So a version is drawn unless a mistake stops AWML drawing it, which the engine's `unsound` gives: every mistake `check` gives but a line that breaks a rule. A version drawn with mistakes says above its drawing how many it has, `workflow.yaml has 1 mistake, drawn in red. See Checks.`, linked to its Checks tab. A push with a mistake is still refused, so only a version stored in an older AWML can be one: a 0.7 version whose untrusted text 0.7 warned of (`test/older-awml.test.tsx`). A list of checks stored at push with a check failed is never drawn. A system's map leaves out a member that doesn't pass check on its own, as before (see "Systems").

## Checks

Added on 2026-10-22. A push with any mistake is refused, so every version passed `awml check` when it was pushed. The Checks tab checks each file again, with the AWML the registry runs (a version pushed since AWML listed its checks shows the list stored at push instead; see "Every check" below), and shows for each file: its name, the AWML that checked it (the release and commit `vendor/awml/version.json` pins, which `npm run engine:update` moves and `npm run engine:build` builds), and each check with its result, "No mistakes" or the mistakes it found. A file with mistakes is not drawn, unless each is a line its drawing draws red (see "Drawings"): its view says how many it has and links to Checks. A version has one file, `workflow.yaml`, which AWML's check checks with the security rules for its design and the platform rules for each implementation; a version stored before 0.4 has its security and platform files. A file stored in an older AWML is checked, as it is drawn, converted to 0.8 (see "AWML 0.8 files"); what converting it noted for its author to do by hand is listed under the file's name, and fails nothing; a file that can't be converted has one row, `awml convert`, with the reasons it gives as its mistakes, and is not drawn.

AWML 0.4.0's check also gives warnings, such as a `do` step that AI decides. The Checks tab lists a file's warnings under its mistakes, with their count beside the result, and says they don't fail the check: a file with only warnings passes, is drawn, and its tab still carries the tick. A push is never refused for a warning. AWML 0.7 added four (chrismdp/awml#108): `warn.several-workflows`, a file whose triggers start separate workflows; `warn.unlinked-part`, a part no line links to a trigger; `warn.untied-comment`, a comment tied to nothing; and `warn.unstarted-step`, a step no trigger's run reaches. Each is a row of the Checks tab by its id, and a push answers with every warning AWML gave, by its check's id (from 2026-10-27, issue #63; `test/one-file.test.tsx` holds `test/fixtures/loose-ends.yaml`, which has all four). AWML 0.8 made one of 0.7's warnings a mistake: untrusted text reaching an outside action with nothing to stop it or accept the risk, `warn.untrusted-outside`, is now `untrusted.outside`, which fails, so a push with it is refused, and a 0.7 version stored with the warning lists its checks now and fails (issue #89).

AWML 0.4.0's check gives only the mistakes it finds. It names no rule and does not list the checks it ran, so each file had one row, `awml check` itself (now only a file stored before 0.4; see "Every check, for workflows pushed before" below), and the page says so, with a link to the part of AWML's spec that says what `awml check` reports.

**Every check, from AWML 0.5.1.** Decided 2026-10-23. AWML 0.5.1 lists every check it runs (chrismdp/awml#38), in its spec's order, each with a stable id, a name, what it guards and a result: `pass`, `fail`, `skipped` or `warn`. A push stores that list for the workflow file with the version, with the AWML that ran it (the release and commit in `vendor/awml/version.json`). The Checks tab of such a version shows one row per check: its name and id, "Passed", the mistakes it found, "Skipped" with why it did not apply, or its warnings, marked as warnings that don't fail the check; then what the check guards. The file is headed with the AWML that made the list, not the one the registry runs now, and the tab carries its tick only when no check failed. A file whose list has a failed check is not drawn. The API's answers are as they were; the list is not in them.

**Every check, for workflows pushed before.** Decided 2026-10-24. A workflow file with no stored list, pushed before the list was stored, has its checks listed when its Checks tab is shown, by the AWML the registry runs, of the file converted to 0.8, and shows one row per check the same way. Its file is headed with the AWML the registry runs, the intro says the file is checked again here, and its tab carries the tick only when no check failed. So does a listed file the AWML the registry runs now finds mistakes in, which only a newer AWML can: the tab shows the list made now, with those checks failing. A list made now is never written into the version; a stored list is always shown as stored, except that a workflow whose refs name a workflow the viewer may see has its checks listed now, against what they name (see "References between workflows"). Only the security and platform files of versions stored before 0.4, which AWML's list doesn't cover, keep the one `awml check` row and the line saying AWML lists the mistakes it finds, not each rule it checks.

## Access

A private workflow is visible to its organisation's members and to nobody else, or, on a user's own account, to that user and to nobody else.

- **Public workflows** can be read by anyone, signed in or not. Only their owner can push to them: the user, or the organisation's members.
- **Private workflows** can be read only by members, or by the user whose own they are. Anyone else gets a 404, the same as for a workflow that doesn't exist, so a private workflow's name never leaks. A push from anyone else gets the same 403 whatever is at the slug, a private workflow, a public one or none, such as `Only members of acme can push here.`, so a push never says a private one is there either. The same holds for platforms and systems. Decided 2026-10-27; until then a push to a private item got a 404 and one to a missing item the 403, which told them apart.
- **Owners** manage members. **Members** read and push. A token acts as its user and can do nothing more. So does an AI client's OAuth token, on `/mcp` only.
- **A token that is not valid**, revoked or mistyped, gets a 401 that says to log in again, from the API, the YAML downloads and the organisation forms alike. It gets the same answer whatever it asks for, so it never learns whether a private workflow exists. A request with no `Authorization` header is anonymous. Decided 2026-10-22, after a self-hosting trial found a revoked token silently read as nobody.
- **A user's own private workflows** (owner is a user). A user's first push may set `private`, through the API, `awml push --private` and the MCP `publish` tool. Only that user reads and pushes it: another user, a signed-out visitor, and the owners and members of any organisation the user belongs to all get the same answers as for a missing workflow, a 404 when they read it and, when they push to it, the 403 `Only ana can push here.` The edition's `privateWorkflowLimit` says how many a user may keep; a first push that would go over it is refused with a 403 that says the limit, how many the user has and that an organisation has no such limit, such as `ana can keep 20 private workflows and has 20. An organisation has no such limit: push it to one of yours, or make it public.` New versions of a private workflow already kept are never refused for the limit. A workflow cannot yet be made public or deleted, so neither frees a place; the limit counts the user's private workflows as they are, so either would once it can. Nothing about a user's own workflows goes in any audit log; they are theirs alone. ## Usernames

Added on 2026-10-22. A person's username starts as the part of their email address before the `@`, made free at their first sign-in. They can change it on Settings, with `PATCH /api/v1/me` (a registry token or a browser session) and with the `set_username` tool on `/mcp`. Each acts only as the signed-in person and names no one else, so nobody can change another person's username. Better Auth's own update-user endpoint refuses a username.

**The rules** are an organisation's slug's: 1 to 40 lowercase letters, digits and single hyphens, starting and ending with a letter or digit, not reserved, and not held by a person or an organisation. A name is trimmed and lowercased first. The refusals say which rule: `Use 1 to 40 lowercase letters, digits and single hyphens, starting and ending with a letter or digit.`, `"settings" is reserved.` or `"bea" is taken.`

**What moves.** Workflows, platforms, versions and memberships are stored against the account, so they all appear under the new name at once, and the versions a person pushed show their new name. Each organisation the person belongs to records a `member_renamed` event, `olive to olive-new`, shown as "renamed" in its audit log.

**Old addresses.** A name a person gave up is kept in the previous names table. While no person or organisation holds it, every address under it answers with a 308 to the same address under the person's current name: the pages (`/{old}`, `/{old}/{slug}`, its versions, every view of each, inventory and settings, and `/{old}/platforms/{slug}` with its versions and tabs, which an old platform address, `/platforms/{old}/{slug}`, reaches first), and, query kept, the YAML and platform downloads and every `/api/v1/{old}/...` and `/api/v1/platforms/{old}/...` route, pushes included. An old `?view=` address goes first to its view's own address, and from there to the new name. A 308 keeps the method and body, so a command line that follows redirects keeps reading and pushing. The redirect is the same whether anything is at the address or not, and the address it sends to makes its own access check, so it tells nobody anything about a workflow. After several renames, every old name leads to the current one.

**When the redirect stops.** An old name is free for anyone to take: a person renaming, someone signing up, or a new organisation. Once someone holds it, their page is there and the redirect stops. If a person takes the name and later gives it up, it redirects to them, as the last person to give it up. A person who takes back their own old name has their page there again, and the name they left redirects to it.

**`/mcp`** tools follow an old name as the API does. Each tool that takes an owner, a workflow (`owner/slug`) or a platform (`get`, `list`, `publish`, `get_platform`, `add_platform` and `fit_workflow`) reads an old name as the person's current one while no person or organisation holds it, and its answer names the current address, so the AI app learns the new name. Writes to an old name go to the person's current name, by the usual push rules. An old name someone else has taken is theirs. The tool checks access under the current name, so an old name never shows anyone a private workflow or platform they could not see under the new one. Decided 2026-10-22, after an AI app that remembered an old address got `Not found.`.

| Negative | A taken, reserved or badly formed name is refused with a clear message on all three, and nothing changes; nobody can change another person's username, whatever the request names; a signed-out request gets a 401, and Settings sends them to sign in; a revoked or made-up token gets a 401 from the API and `/mcp` |
| Cross-tenant | Renaming moves only the person's own pages, never another person's or an organisation's; an old name now held by an organisation never redirects, and its private workflow is the same 404 to the name's former holder and to a stranger; a redirect sends a stranger to the new address, where a private workflow is still a 404 |

## Forks

Added on 2026-10-25 (issue #46). Anyone could read a public workflow, but building on one meant copying its YAML by hand, and nothing then said where it came from. A fork copies one version of a public workflow into an owner of the person's own, and the registry records where it came from. It is also how a system gets an editable copy of another owner's public member (chrismdp/awml#94): fork it, then put the fork in the system.

**Where.** The Fork button beside a workflow's header's version opens a small form: an owner, out of the person and each organisation they belong to; a slug, the original's by default; and public or private, public by default. A signed-out visitor's Fork leads to sign in first. `POST /api/v1/{owner}/{slug}/fork` and the MCP tool `fork_workflow` do the same, and all three call `forkWorkflow` in `src/server/registry.ts`.

**What it copies.** The version being viewed: the latest from the workflow's own page, version n from `/v/{n}`, and `version` in the API and the tool. The fork starts at its own version 1, holding that one file byte for byte, or for a version stored in an older AWML, the file converted to 0.8, since the fork's version is a push and a push takes only 0.8 (from 2026-10-27); the original's history isn't copied. A version stored before the registry took AWML 0.4 files has no workflow file and can't be forked, with a 422 that says so. The fork's first version goes through a push's path: its checks, the edition's `canPush` and `canKeepPrivate`, and the private workflow limit on a person's own account. A fork into an organisation records a `push` in its audit log, as a push does.

**What it records.** The fork stores the source version's id as `forked_from`, never a name, and the file is never changed. Its header says "Forked from **owner/slug**, version n", linked to that version, and the API's answers give `forkedFrom: {owner, slug, number}`. If the original is later private to the viewer, or deleted, the header says "Forked from another workflow", with no name or link, and `forkedFrom` is null.

**The original's forks.** A workflow's side panel ends with "Forks" and how many, listing the forks the viewer may see, of any of its versions, newest first, 20 at most, each with the version it came from. Only forks the viewer may see are listed or counted: public ones, and private ones of the viewer's own account or their organisations. A private fork is never shown to the original's owner or anyone else outside it, not in the list and not in the count, so the count does not leak that it exists. With none to show, the panel has no Forks section.

**Rules.** Only public workflows can be forked: anyone who may not read a private one gets the 404 a missing one gives, and a member who may read it gets a 422 saying only public workflows can be forked. A person forks only into their own account or an organisation they belong to, as an owner or a member, since both may push there; anything else is the 403 a push gives, asked as if the slug were free, so it never tells whether a private workflow is there. A slug already taken in the owner is a 409. One owner may fork its own public workflow into an organisation, or the other way round. A private fork may do everything a private workflow may, and the original's owner learns nothing of it. A fork does not follow the original's new versions, and its page does not say the original has moved on.

| Boundary | Test (`test/fork.test.tsx`) |
|---|---|
| Positive | A person forks a public workflow to themselves and to their organisation, public and private; the fork's file is byte for byte the source version's, or its conversion to 0.8 for a stored 0.4 version (`test/older-awml.test.tsx`); the fork is version 1 and names its source |
| Negative | A stranger forking a private workflow gets the same 404 as for a missing one; nobody forks into another person or an organisation they don't belong to; a signed-out caller gets a 401; a taken slug is a 409; the private limit applies to a fork |
| Cross-tenant | A private fork is never listed or counted on the original's page for its owner, a stranger or a visitor; a fork of an original now private to the viewer, or deleted, names nothing, on its page and in the API |
| Invalid token | A revoked or made-up token gets the same 401 for forking a public, a private and a missing workflow |
| Roles | An organisation's owner and member both fork into it, and each fork is recorded as a push |

## References between workflows

Added on 2026-10-27 (issue #48), for AWML 0.6, which let a part carry `ref:` naming another workflow's part (chrismdp/awml#10): `owner/slug#id` for a published workflow, or a path to a file alongside, such as `shopping.yaml#list`. The referring workflow keeps its own full copy of the part, so it still checks alone. A ref follows the latest version of what it names; there is no pinning. The code is in `src/server/refs.ts`.

**Starting another workflow (AWML 0.7, issue #63).** A trigger never has `ref` in AWML 0.7, and no line but a tie or a hidden one goes into a trigger (chrismdp/awml#109). One workflow starts another with an outside action, reached from a `do` step and with a tier, such as `Start the supplier order: Allow`, whose `ref` names the other workflow's trigger, as `owner/slug#id` or a path such as `bakery-order.yaml#low`. The registry takes it as any ref: a path is rewritten on publish, it is checked against the workflow it names, and the drawing links the action to that workflow's page, with its trigger in the fragment. The action's mark says `Starts owner/slug#id`, or `Starts a workflow you can't see`, and the trigger's, on the started workflow's page, `Started by owner/slug`, when the referrer's ref starts it: its referring part is an outside action, as its push stored it, from the file as the engine read it, and the part it names is a trigger, which the started workflow's page checks from its own file. Any other referrer, such as one whose outside action names a part that isn't a trigger, is listed as `Used by`, and a stored 0.6 workflow whose trigger with a ref converts into an outside action starts it. A page reads only these stored answers about the workflows that refer to it, never their files. A platform's own hand-off, such as CI finishing, is named in the receiving trigger's label and isn't linked. Untrusted text follows the action into the workflow it starts when the two are given together (chrismdp/awml#112), as a system's members are (see "Systems"), and as a workflow's Checks tab gives it with the workflows its refs name; the checks stored at push are of the file alone, which is unchanged.

**A path ref is rewritten on publish.** A push whose file has `ref: shopping.yaml#list` is stored with `ref: {owner}/shopping#list`: the owner is the one pushed to, and the slug is the file's name without `.yaml`. Only the ref's own text changes, in the quotes it was written in; every other byte is as pushed. The push answers with each rewrite it made, as `rewrites` from the API and the MCP `publish` tool. No map of file names is sent, from the CLI or the MCP tool: `awml push owner/slug file` takes the slug apart from the file's name, so a file that others refer to by path must be published under its name without `.yaml`, and anything else is written as `owner/slug#id` in the first place. A path that leaves the folder, such as `../shopping.yaml#list` or `lists/shopping.yaml#list`, isn't a `.yaml` name, or whose name can't be a workflow's slug, is refused with a 422 that names the part and the ref.

**Checked against what they name.** The engine never fetches from the registry, so the registry gives AWML's `check` the referring workflow with the latest version of each workflow it refers to, each at a path ending `owner/slug.yaml`, which is how the engine follows an `owner/slug#id` ref. It reports a copy that disagrees on kind, label or `at`, a ref to a part that doesn't exist, and scopes that differ in their people or terms; only the referring file's own mistakes are shown. At push, a mistake refuses the push, as any check's does. The checks stored with a version are the file's checks alone. The Checks tab lists, above the checks, each ref and what it names: a workflow the viewer may see, linked; `owner/slug#id, not pushed yet`, when nothing is there and the viewer may see every workflow of that owner; or "a workflow you can't see", unnamed, for anything else, private or missing alike, with no check against it, so nothing about it leaks. When the viewer may see any workflow the refs name, the tab's checks are listed now, by the AWML the registry runs, against those workflows' latest versions, so a copy that disagrees after the workflow it names changes is reported there. A version is drawn when its file checks alone, so that report doesn't stop its drawing.

**Who may refer to what.** A public workflow may refer only to public ones: a public push whose refs name a private workflow, or one that doesn't exist, gets a 422 naming each such ref, `workflow: part "list" refers to acme/secret#list, but a public workflow may refer only to public ones, and acme/secret is not one.`, the same for a private workflow as for a missing one. A private push may refer to anything, so a set of files can be pushed in any order: it is checked against what its owner may see, the public workflows, the owner's own, and for a person, their organisations' private ones; anything else, a workflow not pushed yet or another owner's private one, is left unchecked, the same either way. A workflow that a public one refers to and that is later made private is allowed; the public referrer's refs then show as "a workflow you can't see" to anyone who may not see it, and its YAML still holds the address, which was public before.

**Referred to by.** A workflow's side panel has "Referred to by" and how many, listing each workflow whose latest version has a ref to one of its parts, with the parts it names, worked out from the refs stored at push, by owner and slug. Only referrers the viewer may see are listed or counted: public ones, and private ones of the viewer's own account or their organisations. With none to show, the panel has no such section. The API's `GET /api/v1/{owner}/{slug}` gives the same list as `referredBy`.

**In the drawing.** Decided 2026-10-27 (issue #55); drawn the registry's own way from 2026-10-27 (issue #62). On the drawing tabs, the security view and the platform view, each part with a ref and each part other workflows refer to carries a small chain mark inside its top-right corner, the same in both views and either way, and a tooltip. The marks are added to the drawing for each viewer from what they may know, after the layout, which knows nothing of who is looking. A ref's tooltip is `Linked to owner/slug#id`, and a click, Enter, or on a touch screen a second tap (the first lights it; see "On the page"), on the part opens `/{owner}/{slug}#{id}`, and Ctrl or ⌘ with a click or Enter, or the middle button, opens it in a new tab, as a link does; a press that drags moves the part and opens nothing. In a browser that runs no scripts the part is a plain link. The part takes the focus, named by its own label and then where it leads, and Tab moves the drawing to show it. The page opened outlines the part its fragment names. A part others refer to says `Used by owner/slug`, or `Used by a/b, c/d and e/f` for several, built from "Referred to by"; with one, following it opens that workflow, and with several, Enter, Space or a press, a second tap on a touch screen, opens a small menu under the part, or above it when only above has room, listing them; Esc or a second press closes it. A part that does both says both, a line each, and its menu lists all. A part with a menu is a button that says whether its menu is open, and closing the menu gives the focus back to it; a part that leads nowhere the viewer may go is still named by where it would lead, and keeps its tooltip, once React Flow draws it too. The marks show only what the Checks tab and "Referred to by" already show the viewer: a ref to a workflow they can't see is marked "Linked to a workflow you can't see", greyed and leading nowhere; a ref to a workflow not pushed yet, to someone who may see its owner, is marked `Linked to owner/slug#id, not pushed yet` and leads nowhere; and a referrer they can't see is never listed or counted. The tests are in `test/part-links.test.tsx`, `test/links.test.ts` and `test/flow-canvas.test.tsx`.

The registry has no admin role, so no boundary below is an admin's.

## Systems

Added on 2026-10-27 (issue #50). AWML has no system file (chrismdp/awml#94): a system is several workflows given to the engine together, which then draws the map of them, checks them together, says who waits across them and judges each platform running them all. The registry keeps a named system of its own, modelled on the stored platform: the same pushing, versioning, owner rules and page layout. The code is in `src/server/systems.ts`, and the page's in `src/app/[owner]/systems/[slug]/load.ts`.

**Stored and versioned.** A system is at `/{owner}/systems/{slug}`, for a person or an organisation, public or private. Each push is a new numbered version that never changes, holding a title, a Markdown description and a list of members as `owner/slug`. A member follows its workflow's latest version: a system version records only which workflows are in it, never a version number, so a member's new version changes what the system shows without a new system version. Private systems count against no limit, a person's included.

**Pushing one.** `POST /api/v1/{owner}/systems/{slug}/versions` and the MCP tool `publish_system` both call `pushSystemVersion`. Whoever may push a workflow to the owner may push a system to it, and the first push sets its visibility, as for a workflow; anyone else gets the 403 a workflow's push gives, `Only members of acme can push here.`, the same whether a private system, a public one or none is there. A system has at least one member, each named once as `owner/slug`. What it may hold is judged by what the system's owner may see, by the rule a workflow's refs go by (see "References between workflows"): a public workflow of any owner, the owner's own, and for a person, the private workflows of the organisations they belong to. So a person's system may hold their own private workflows and their organisations', and an organisation's system only its own and public ones: never a member's personal private workflow, nor another organisation's private one, even when the pusher belongs to both. The pusher must be able to see each member too. Another owner's public workflow is a member read-only; to change one, fork it (see "Forks") and put the fork in. A member the system's owner may not hold, one the pusher may not see and one that doesn't exist are all refused with the same 422, which names the owner's rule: `members: ana/notes is not a workflow acme's systems may hold: a public one, or one of acme's own.` for an organisation, and `members: beta/secret is not a workflow ana's systems may hold: a public one, one of ana's own, or one of an organisation ana belongs to.` for a person. So a push says nothing about a private workflow. The other refusals are `members: name at least one workflow, as owner/slug.`, `members: acme/shopping is named twice.`, `members: "shopping" is not owner/slug.`, `title: give the system a title.` and `description: send it as Markdown text.` A push to an organisation records a `push` in its audit log, as `{owner}/systems/{slug} v{n}`.

**The page.** The header gives the owner, `systems` and the slug, the title, "System", public or private and the version, then the description, rendered as the registry renders any untrusted Markdown: any raw HTML in it shown as text. Beside the tabs, "Workflows" and how many, each member the viewer may see linked to its page by its title, with its `owner/slug`, "private" for a private one, and "not drawn" for one whose latest version doesn't pass check. Each member the viewer may see is given to the engine as its latest version, converted when it is stored in an older AWML (see "AWML 0.8 files"), at a path ending `owner/slug.yaml`, the way "References between workflows" gives a referred workflow, so the engine follows the refs between members. The tabs, as a workflow's page has them:

- **Map**: the engine's map of every member drawn, one box per workflow and the parts they share, by the ref between them, drawn once. With one member drawn, its own drawing. The engine draws each workflow's triggers outside its box, with a line into the box, and each outside action that starts a workflow inside its box, with a line to the trigger it starts (chrismdp/awml#122, from AWML 0.7). Each box is named by the `owner/slug` of the file it was given, and opens that workflow's page (#61, #69): a click, a second tap (see "On the page") or Enter on it, or Ctrl or ⌘ with a click, or the middle button, for a new tab, as a link does; a press that drags moves the box or the drawing and opens nothing. A part joined to workflows' boxes, such as a trigger that starts a workflow, or data they share, leads to those workflows as a part with a ref does (see "References between workflows"): straight to one, or a menu of several. A part marked untrusted is outlined as on a workflow's drawing, red when its text reaches an outside action in any member with nothing to stop it (#83); the map's lines run to the workflows' boxes, so `graph` gives them no untrusted text to draw. An outside action that starts another workflow leads, by the trigger it starts, to that workflow, saying `Starts` and its title. The engine is given only the members the viewer may see, each at a path ending `owner/slug.yaml`, and a box leads only to a member given, so a box, a part and a link that would name a member the viewer may not see are never in the drawing the page is sent.
- **Checks**: every check AWML runs, on the members together, listed for each member as `owner/slug.yaml`, by the AWML the registry runs. A copy of a part that disagrees with the member it refers to is a mistake here, and so, from AWML 0.8, is untrusted text that follows an outside action into the member it starts and reaches an outside action there with nothing to stop it or accept the risk, `untrusted.outside`, on that member (chrismdp/awml#112; a warning until AWML 0.8). Text can only follow an outside action that a standing approval accepting the risk is in front of, since the member that starts the other fails on its own otherwise. Its tab carries a tick when no check failed, or the number of mistakes.
- **Who waits**: from the engine's summary across the members drawn, what waits on a person, each a person's step or a review; then, under "Where untrusted text reaches", each part marked untrusted with the outside actions its text reaches across the members, what stops it, and from AWML 0.8 each outside action whose risk a standing approval accepts, with the approval (from 2026-10-27, issue #63); then the parts the members share and which workflows share each.
- **Where it runs**: the members drawn, judged together against each platform the viewer may see that is the system's owner's or public, as `POST /api/v1/fit` judges a design, one platform at a time: each platform linked, whether it runs them all and every reason it doesn't; or, when the members don't say all the fit needs, the gaps. A private platform judged is recorded as viewed in its organisation's audit log, as the fit records it.

A member whose latest version doesn't pass check on its own is listed, marked "not drawn", and left out of the map, who waits and where it runs; its mistakes show on the Checks tab. When the engine can't work out a map, a summary or a fit for the members together, such as when two copies of a shared part disagree, that tab says what AWML found and links to Checks.

**Private members, hidden.** A public system may have private members: an organisation's own, or a person's own or their organisations'. A viewer who may not see a member gets "1 private workflow", or "n private workflows", at the end of the list, with no name or link, and every tab leaves out every such member: it is never given to the engine for them, so nothing of it reaches the map, the checks, the summary or the fit. Above the tabs the page says `This system is shown incomplete: 1 of its workflows is private to you, so every tab leaves it out.` A member made private after it was added is treated the same way. A deleted member is listed as `owner/slug · missing: it is no longer there, so every tab leaves it out` to the account that owned it when it was pushed, the person or the organisation's members, and counted as a private workflow to anyone else. The member keeps that account, not only its name, so whoever takes the name later is told nothing.

**On each member's page.** A workflow's side panel has "Systems" and how many, a line `In **title**` for each system whose latest version has it as a member, linked to the system, for each system the viewer may see: public ones, and private ones of the viewer's own account or their organisations. A private system is never listed or counted to anyone outside it. With none to show, the panel has no such section. The API's `GET /api/v1/{owner}/{slug}` gives the same list as `systems`.

**Finding systems.** An owner's page lists its systems under "Systems", the public ones to everyone and the private ones to its members, or to the user. The gallery lists the public ones in their own section, "Systems", searched by title as its workflows are.

**Seen privately.** Opening a private system records a `private_view` of `{owner}/systems/{slug} v{n}` in its organisation's audit log, and each private member of an organisation shown on it a `private_view` of that workflow at the latest version shown, `{owner}/{slug} v{n}`, as opening the workflow does.

Not in this: deploying a system as one thing (each workflow deploys alone), systems holding systems, pinning member versions, a web form to make or edit a system, and a `GET` of a system in the API or a tool to read one through `/mcp`.

The registry has no admin role, so no boundary below is an admin's.

## Embedding

Added on 2026-10-27 (issue #75), for a chrismdp.com post that embeds the Counting House workflows and their system. A public workflow's drawing, or a public system's map, can be shown on another site in an iframe:

```html
<iframe src="https://awml.io/chrismdp/counting-house-rung-1-off/embed"
        width="700" height="450" style="border: 0" loading="lazy"
        title="Fernwick Air: rebook after a missed connection, tier off"></iframe>
```

**Its address.** `/{owner}/{slug}/embed` draws the latest version, `/{owner}/{slug}/v/{n}/embed` one version, fixed, and `/{owner}/systems/{slug}/embed` the system's map. With no options a workflow's embed draws who may see each part. `?view=platform` draws where each part runs instead, for the implementation `&implementation={id}` names, or else the first, as the workflow's page picks it; an implementation the version doesn't have is a 404, as on the page. `?flow=1` starts with Flow only on. An owner's old name redirects to the same embed under their new one, with the same options.

**What it shows.** The drawing alone, filling the frame, drawn as on the item's page (see "Drawings"), with pan, zoom, Fit and Flow only, moving as on the page. The frame is compact: its switches are smaller, so a small frame such as 600×400, or a phone's, keeps more of itself for the drawing (`COMPACT_INSET` in `src/components/viewport.ts`). The switches are in the top right and the zoom buttons in the bottom left. In the bottom right a link, `{title} · awml.io`, opens the item's page in a new tab; a self-hosted registry gives its own host. There is no site header, footer or navigation. The root layout reads no session itself and takes its header only from a chrome slot (`src/app/@chrome`), which is empty for the three embed pages, and the embed pages have a layout of their own. An address no route answers has no slot, so its 404 is `src/app/global-not-found.tsx` (`experimental.globalNotFound`), the root layout given the site's header. A workflow or a map that isn't drawn says why in the frame, in the words its page uses. A system some of whose members someone signed out may not see says "1 private workflow left out", and draws nothing of them.

**Links.** Every link in an embed opens a new tab, never the frame: the corner link, a part linked to other workflows and its menu (#55), and a workflow's box on a map (#61).

**Public only.** An embed reads no session or cookie. It is worked out for nobody, by the same code as the item's page (`src/server/embed.ts`), so it shows exactly what someone signed out sees there, a system's members and a part's links included. Nothing around it reads the session either. The root layout never does, and Next renders it twice on every page, the second time with no slots as a hidden 404 for a slot that matches nothing, which is why it never falls back to a header of its own. A private workflow or system gets the same 404 as a missing one, whoever is signed in. Checked through the built server on 2026-10-27: signed in, each embed, a 404 one included, sent byte for byte what it sent signed out, apart from the build's id.

**Who may frame a page.** Only the embed pages may be framed by another site: they send `Content-Security-Policy: frame-ancestors *` and no `X-Frame-Options`. Every other address sends `Content-Security-Policy: frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN`, so sign-in and settings can't be clickjacked. The rules are in one place, `headers()` in `next.config.ts`, which OpenNext applies in the Worker from the routes manifest. One pattern gives the embed pages' addresses, and the other rule takes every path it doesn't match, so each address gets one set of headers or the other. The pattern never takes another page's address for an embed's. It leaves out an owner or a slug kept for other pages, such as `/api/auth/...`, `/platforms/...` and `/{owner}/platforms/...`, a name in another case, and anything after `embed`. Next's own server matches these headers with case, as the Worker does, because `experimental.caseSensitiveRoutes` is set.

**Speed.** An embed is worked out as the item's page is, by the same reads and the same engine calls, so each server's kept engine answers and layouts serve both. It reads nothing the page doesn't, and never the session. Counted through the built server on 2026-10-27, signed in, an ordinary page looks the session up twice, once for its header and once for the page itself, as before #75, and an embed not at all. An embed is sent with the same headers for caching as the page.

**On awml.io's home page.** The hosted repo can show the same drawing inline. It renders `EmbeddedDrawing` from `src/components/Embed.tsx` with the props `workflowEmbed(owner, slug, n, options)` or `systemEmbed(owner, slug, options)` give (`src/server/embed.ts`), inside an element with a height of its own.

The registry has no admin role, so no boundary below is an admin's.

## The MCP server

Added after v1, on 2026-10-22. A person connects their own AI (Claude.ai, Claude Desktop, ChatGPT, Claude Code, Codex) to `<registry>/mcp` and asks it to check, read or publish workflows. It runs on their account, not ours; the registry still sends nothing to a model.

**Tools.** Each calls the same functions in `src/server` as the website and the API, so it sees what the person may see and the audit log records the same events (`push` on publish, fork_workflow, add_platform and publish_system, `private_view` on reading a private workflow or platform, or fitting against a private platform, `member_renamed` on set_username). A tool given a username its person has since changed follows it to their current one (see "Usernames").

| Tool | What it does |
|---|---|
| `check` | Checks a workflow's AWML 0.8 file, sent as `workflow`, with the AWML engine, and gives the mistakes. Refuses an older AWML as a push does. Saves nothing |
| `publish` | Saves a new version of `owner/slug` from its AWML 0.8 file, sent as `workflow`, by the same rules as `POST /api/v1/{owner}/{slug}/versions`. Gives the page `<registry>/{owner}/{slug}`, the version number and, as `rewrites` and a line each, every path ref it stored as `owner/slug#id` (from 2026-10-27), and as `warnings` and a line each, every warning AWML gave the file, by its check's id (from 2026-10-27) |

| `get` | A workflow's YAML (`workflow.yaml`, or for a version stored before, its security and platform files), check result and summary, the latest version or a given one |
| `list` | An owner's workflows the person may see; with no owner, their own and their organisations' |

Gives the same answer as `POST /api/v1/fit` |

Every `url` a tool gives is a page a person can open, never an API address, so an AI app can show it to its person. The platform tools gave the API's address until 2026-10-22, when they were changed to give the platform's page.

The person's own AI reads a platform's recipe and does the installing. The registry neither runs a recipe nor sends anything to a model, and the fit is code.

**Signing in, two ways, both the same person.**

- OAuth 2.1 through Better Auth's MCP plugin (`@better-auth/mcp`). The client names itself by the https address of its client ID metadata document (CIMD, Better Auth's `@better-auth/cimd` with the MCP 2026-07-28 profile), as Claude.ai's custom connectors do by default, or registers itself with dynamic client registration. The sign-in server's metadata offers both. An AI client finds it from the address alone: `/mcp` answers a request without a token with a 401 whose `WWW-Authenticate` names the protected resource metadata, which names the sign-in server. The person signs in on `/login` as usual and allows the client on `/consent`. The access token is a JWT for `/mcp` only.
- `Authorization: Bearer <registry token>`, a token from `/settings/tokens`, for clients that take a header.

**Every request to `/mcp` needs one of them, reads of public workflows included.** AI clients decide whether a server needs signing in when they first connect, so a server that answers anonymously never gets signed in to. Anyone can still read public workflows without an account on the website, through `GET /api/v1/...` and with `awml pull`. Decided 2026-10-22, over letting anonymous callers read public workflows through `/mcp`.

Every address the sign-in metadata gives comes from `BETTER_AUTH_URL`, so a self-hosted registry's `/mcp` works the same at its own address.

**Fetching a client's metadata document** reaches only public addresses. Better Auth refuses a `client_id` whose host is a private, loopback, link-local or reserved address, gives up after five seconds and reads at most 5 KB; `src/server/client-metadata.ts` stops waiting at the five seconds even while a name is still being resolved. Under it, in Node (the Docker image), Better Auth's own transport resolves the name once, refuses unless every address is public, connects to that address only and never follows a redirect. On a Worker, which cannot choose the address it connects to, the name is resolved first over DNS over HTTPS and fetched only when every A and AAAA answer is public, without following a redirect. The tests are in `test/client-metadata.test.ts`. Added on 2026-10-22, after Claude.ai's custom connectors defaulted to CIMD and a person had to choose dynamic registration by hand.

## Platforms and the fit

Added after v1, on 2026-10-22, for AWML 0.3, moved to AWML 0.4 the same day, to 0.4 and 0.5 on 2026-10-23, to 0.6 on 2026-10-27, to 0.7 later that day and to 0.8 on 2026-10-28. AWML's spec says where a workflow can run (its section "Placing a workflow: where it can run"). A workflow's design says what it needs: who may process each scope (`processing`), how long work may wait after each trigger (`wait`) and where each existing context is kept (`at`). A **platform description** says what one platform offers: how long it may be off, whether the workflow's own code carries out its steps or an agent does, whose agents run there, which models its code can call and which folders it holds. The fit matches the two.

**A platform** is an item of its own: an owner, a slug, a visibility and numbered versions that never change, the same as a workflow. Each version holds:

- **the description**, AWML's platform description as YAML, marked `awml: "0.8"`. An older one is refused with a 400: ``This registry takes AWML 0.8 platform descriptions. Upgrade yours with `awml convert description.yaml > upgraded.yaml` and push that.`` A description stored before, marked `"0.4"`, `"0.5"`, `"0.6"` or `"0.7"`, is kept as it was pushed, and converted to 0.8 whenever the fit reads it; its page reads its fields as stored, since 0.6, 0.7 and 0.8 changed only the version, and its YAML tab says it is shown as pushed and that the fit reads it converted to AWML 0.8. The id may be the platform's own address, `owner/platforms/slug`, as `awml pull` writes it; one that gives another platform's address is refused with a 422: ``description: the platform id "<id>" must be <owner>/platforms/<slug>, where it is pushed, or a bare id.`` It is checked at upload by the AWML engine and refused with `awml check`'s messages, each starting `description: `. A workflow sent as a description is refused, and so is a description sent as a workflow's file. The platform's label is the one its latest description gives.
- **an install recipe**, optional: Markdown steps an agent follows to install a workflow on that platform. It says what to create, where each secret goes, how to schedule the triggers and how to check the workflow is running. It never holds a secret itself. The registry stores and serves recipes, and never runs them.

**The fit.** `POST /api/v1/fit` takes a JSON body:

- `workflow`: `owner/slug` or `owner/slug@n`, a stored workflow: its file, or for a version stored before 0.4, its security view, either converted to 0.8 when stored in an older AWML; or `file`: a workflow's AWML 0.8 file as YAML (`security` is taken as `file`, for callers of the 0.3 API). One of the two, not both. YAML marked as an older AWML is refused with the push's 400.
- `implementation`: optional, the id of one of the workflow's implementations, as `awml fit --implementation` takes it. A workflow without it is refused with a 422.
- `platforms`: optional, a list of `owner/slug` or `owner/slug@n`. Without it, the fit runs against every platform the caller may see: the public ones, and the private ones of the organisations they belong to. Each platform named must be one the caller may read; a private platform of another organisation answers `404 Not found: owner/slug.`, exactly as a missing one does.

Without `implementation`, it judges the design, and answers 200 with `{workflow, implementation: null, results, gaps}`. `workflow` is `{owner, slug, number}`, or null for YAML. Each result is what `awml fit --json` gives for that platform, `{judged, fits, reasons, models}`, with `platform` as the registry address `owner/slug`, plus the version `number` and the description's `id` and `label`. When the workflow doesn't say what the fit needs, such as a scope without `processing` or a trigger without `wait`, `gaps` lists them and there are no results. The API answers anyone, signed in or not, as it does for reading; a token that is not valid gets the 401.

The registry gives the engine one platform at a time for the design, so no platform's description reaches another's answer, and two platforms whose descriptions share an id are both judged.

With `implementation`, it judges that implementation's placement: each block that names a platform is judged against the platform among those the fit runs against that it names, and a block that names none is not judged. A block names a platform by its description's id, or by the platform's registry address, `owner/platforms/slug`, as AWML 0.5 first allowed. A bare id is matched with the description's id. An address is matched only with the platform at that address, whatever id its description has: the registry gives the engine that description with the address as its id, so `awml fit` pairs them with no network, as AWML 0.5 decided (awml#71). The answer has `implementation` and one result per block, as `awml fit --json --implementation` gives it, with `block` as the block's id and `platform`, `number`, `id` and `label` of the platform judged, or null when it names none. A block naming an id or an address no such platform has is a gap, in the engine's words, so a private platform of another organisation is never judged or named, whichever way the block names it. Two such platforms with the same id answer a 422 asking for `platforms` to name one.

Each private platform judged is recorded in its organisation's audit log as a view.

This repo seeds no platforms. AWML's example platforms are in `test/fixtures/platforms`, copied by `npm run engine:update` with what the native `awml fit --json` says of them, so the tests compare the registry's fit with the CLI's.

**Pages.** `/{owner}/platforms` lists an owner's platforms, and `/platforms` the shared ones (see "Pages, API and CLI"). An owner with no platforms gets a page that says what a platform description is, field by field, and that `awml fit` checks workflows against it; to those who may add one there, it also gives the registry's MCP address with a request to ask their own AI (add a platform, then fit a workflow against it), the API command that pushes the file, and that each change is a new version and the fit uses the latest. Under a list, members get the same help in short. Added on 2026-10-22.

**Pulling.** AWML 0.5.0's `awml pull owner/platforms/slug` asks for `/api/v1/{owner}/platforms/{slug}`, and the registry answers there as it does at `/api/v1/platforms/{owner}/{slug}`: a private platform is a 404 to anyone outside its organisation, as a missing one is. Added on 2026-10-23.

Not yet: a page for where a workflow can run.

## AWML 0.8 files

Added on 2026-10-22 for AWML 0.4. AWML 0.4 keeps each workflow in one file: the design (scopes, parts and lines), plus `implementations`, each a named running system that places the parts in blocks, a block being a platform. AWML 0.5, taken from 2026-10-23, kept that file and let a block's `platform` name a registered platform as `owner/platforms/slug` (see "Platforms and the fit"). AWML 0.6, taken alone from 2026-10-27 (issue #47), kept it again; its engine read only 0.6 files, and `awml convert` upgraded a file of any older version in one step. AWML 0.7, taken alone later that day with AWML 0.7.1 (issues #63 and #69), keeps the file and starts another workflow with an outside action (see "References between workflows"). AWML 0.8, taken alone on 2026-10-28 with AWML 0.8.0 (issues #83 and #89), keeps it again: a standing approval may now cover an action that can't be undone, or a public one, when its label says who accepted the risk and on what evidence; untrusted text reaching an outside action with nothing to stop it or accept the risk is a mistake; and the fork is gone. Its engine reads only 0.8 files, and `awml convert` upgrades a 0.7 file, or any older one, in one step. The registry draws, checks and fits every file with the AWML engine it runs.

**Pushing.** A push sends one file, as `workflow`, through the API, `awml push` or the MCP `publish` tool, and the MCP `check` tool checks one the same way. A file marked as any other AWML, in any field, a 0.7 file included, is refused with a 400: ``This registry takes AWML 0.8 files. Upgrade yours with `awml convert workflow.yaml > upgraded.yaml`, or join a 0.3 pair with `awml convert security.yaml platform.yaml > upgraded.yaml`, and push that.`` A file that names no AWML at all, or isn't YAML, is left to `awml check`, whose 422 says what is wrong. More than one file, or a platform description, is refused with a 422. An older `awml push` therefore fails until its person upgrades it.

**Versions stored in an older AWML** keep their files as they were pushed, and are never rewritten: no migration and no second column. Each time one is read, the engine's WebAssembly `convert` upgrades it to 0.8 (`src/server/as-read.ts`), and the page, the Checks, the fit and a gallery card use the result; a convert is a few milliseconds, like a check. Converting a 0.6 file changes only lines into a trigger that has `ref`: where only `do` steps lead into it and nothing leads out, the trigger becomes their outside action, keeping its `ref`, gaining `: Allow`, and losing its `wait` and any `untrusted` mark, with a note that the mark belongs on the started workflow's trigger; any other line into a trigger stays, and the converted file's checks report it for its author to redraw, so it is not drawn. Converting a 0.7 file changes only its version, unless it has a fork: each fork goes, and each line into it is joined to each line out of it, keeping the line out's kind and label, or the line in's label where the line out has none. A 0.7 file whose untrusted text reaches an outside action with nothing to stop it converts with that mistake, which its Checks tab shows and its drawing draws red. `awml convert` exits 1 when it notes something or finds mistakes, and still prints the whole file; the registry reads that file, never taking the exit as a failure, and shows the notes, which fail nothing, on the file's Checks tab and under the line on its YAML tab. Its YAML tab and its raw file give the stored bytes, the tab under a line such as `workflow.yaml is AWML 0.4, as it was pushed. The registry draws, checks and fits it converted to AWML 0.8.` The checks stored at push stay as stored, named by the AWML that made them; a version with none has them worked out when shown, from the file converted. Its summary is the one worked out at push. A platform description stored in an older AWML is read the same way (see "Platforms and the fit"). The tests, a stored 0.4 workflow, a stored 0.5 workflow, a stored 0.5 platform description, a stored 0.6 workflow whose do step leads into another workflow's trigger, and two stored 0.7 workflows, one whose untrusted text 0.7 warned of, each shown, checked, drawn and fitted through `convert` as the native `awml` does the converted file, the 0.6 one with what converting it noted and the 0.7 one with its untrusted text failing and drawn red, and every older push refused, 0.7 included, are in `test/older-awml.test.tsx`.

**Versions stored before 0.4** hold their security file, their platform file or both, as they were pushed. Their pages, YAML, Checks and file downloads work as before, through `convert`: a security file converts on its own into a workflow whose design is drawn, and a platform file only joined with its security file, whose one implementation it then draws. `convert` refuses a pair whose views differ in their parts or lines, and a platform file stored alone, so such a platform view is not drawn, and its Checks give `convert`'s reasons. They have no implementations, so `/platform/{implementation}` is a 404 for them. A stored security view can still be fitted by name.
