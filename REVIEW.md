# Reviewing a change to the AWML Registry

This says what failure looks like in this repository. The reviews on every pull request hold every change to it, and a person reviewing by hand can use it too. `docs/SPEC.md` is the authority on what the registry does and why, and its "Access" section on who may see and push what. `AGENTS.md` says how the repository is worked on.

A finding is **Important** when the change breaks one of these, or does something else that would be wrong on main. It's a **Nit** when it works but could be clearer or simpler. It's **Pre-existing** when the fault was there before the change and the change only passes near it.

## What failure looks like

- **The code drifts from the spec.** The registry does something `docs/SPEC.md` doesn't say, or says it doesn't. A change to what the registry does updates the spec in the same change, with the date it was decided, as the spec's own entries do, and the README where it tells people how to use the registry.
- **Something private leaks.** A private workflow, platform or system, a person's own private workflows, and an organisation's members and audit log are seen only by those the spec's "Access" section names. Anyone else gets exactly the answer a missing one gives: the same 404 on a read, the same 403 on a push, the same 422 for a ref or a system's member, and nothing in a list, a count, a search, a redirect, a drawing's link or tooltip, the fit's results and reasons, or an error message. A leak can be a difference in any of those, not only the item itself.
- **A boundary goes untested.** A change to who may read or push covers the boundaries the spec's tables list, each with a test: positive, the right person can; negative, anyone else can't, and is answered as for a missing item; cross-tenant, one organisation's or person's token never reaches another's; and roles, an owner and a member each doing exactly what their role allows. The registry has no admin role, so no path may let anyone past these. A token that isn't valid gets the same 401 whatever it asks for.
- **Sign-in acts beyond its person.** A registry token, a Better Auth session and an AI client's OAuth token each act as their one person and can do nothing more, and the OAuth token only on `/mcp`. A bearer token that isn't valid is refused with a 401, never taken as nobody. A token's secret is shown once and only its SHA-256 hash is kept, so a secret never reaches a log, a page after it was made, or the database. Disconnecting an app or revoking a token touches only that person's.
- **An MCP tool goes its own way.** Each tool on `/mcp` calls the same functions in `src/server` as the website and the API, so it sees what its person may see, records the same audit events and follows an old username the same way. Every `url` a tool gives is a page, never an API address. Every request to `/mcp` needs a sign-in, reads of public workflows included.
- **A statement binds more than D1 allows.** Cloudflare D1 binds at most 100 values in one statement, and SQLite far more, so a statement that passes locally can fail on awml.io. Rows go in groups through `insertRows` in `src/db/rows.ts`, and a list that grows with the data is read by a join or a subquery, never a list of values. `test/setup.ts` refuses any statement that binds more, but only at the sizes a test uses, so a list that grows with the data needs a test past 100.
- **Pushed text reaches a page as code.** A workflow's YAML, a platform's description and recipe, a system's description, a note, a label, a title and a username are all a person's text. A page shows them as text, renders Markdown with raw HTML shown as text, and links only where the registry builds the link. The engine's Mermaid text is read back as data, never put into a page as markup.
- **A request outgrows a Worker.** awml.io runs on Cloudflare Workers, which limit a request's CPU time and a Worker's memory. A drawing is laid out on the server only within `LIMITS` in `src/server/drawing.ts`, the caches keep at most 200 answers of each kind, and reading the engine's text looks at each character once. A change that lays out more, keeps more, or does work that grows faster than its input must show it stays within the limits, and no part of ELK may reach the browser.
- **Code that only runs on Node.** `next.config.ts` swaps four modules for Worker ones when building for Cloudflare. Anything else that reaches the Worker uses no Node-only module, such as `fs`, `net`, `better-sqlite3` or `nodemailer`. Fetching an AI client's metadata document reaches only public addresses, on Node and on a Worker.
- **The registry and the CLI disagree.** Checks, fits, conversion and the graph a drawing is made from come from the AWML engine in `vendor/awml`, so the registry gives the same answers as `awml`. The registry never works out for itself what the engine judges. A version stored in an older AWML is converted when it's read, never rewritten.
- **Output whose order isn't fixed.** A list on a page, in the API or from a tool comes out in the same order every time. A query without an `ORDER BY` and a tie-break, or a sort without one, gives a page or a test that changes from run to run.
- **Billing code.** This repository has none. Anything to do with payment belongs in the hosted service, behind the edition hook in `src/edition.ts`.
- **Untrusted text reaches an outside action.** Text from an issue, a comment, a pull request, a log or a model never decides what a workflow pushes, merges, labels or comments, except as data that a person or a code rule reads. A path, a number or a name taken from such text is checked before it's used.
- **Event, issue or Claude text goes into a `${{ }}` expression in a workflow.** Inside `run:`, such text reaches the shell only through `env:`, quoted. A `${{ }}` that expands it in the script lets the text run as code.
